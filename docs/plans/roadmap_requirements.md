# Roadmap 编写与验收要求

版本：v0.2
日期：2026-09-21（随 GOV-002 入库；2026-09-20 晚会议新增执行纪律）
来源：叶安提出，参照 26isip_Aerospace 无人机项目的"执行路线即唯一基线 + 机器验收 + 可视化验收"机制，结合本仓库既有 [验收规范](../ACCEPTANCE.md)；2026-09-20 晚会议新增执行纪律（每步三文档时序、AI 开工协议、git 同步、草稿不入库、AI 产出人工核查）；ZCode 整理代拟。
地位：**已生效**——roadmap 是对应工作范围的唯一执行基线；第 2 节执行纪律对全体成员与 AI 即日生效，§6 待并入治理文件的条目在 R0 评审后随小 PR 并入。本文只规定 roadmap 必须包含什么与怎么执行，不替任何工作线预定技术结论。

## 1. 为什么需要这个要求

当前问题：整体 roadmap 缺失，工作线之间只靠会议口头对齐，导致（a）交付物形式无标准——数据线交付了契约却没有清洗执行计划，没人能指着文档说"还缺什么"；（b）每一步"做完"没有统一判据；（c）口径（标签窗、折分、版本）各自理解、数字不可比。

规则：**执行任何一步之前，该步必须已落实在某个 roadmap 中**——写明具体操作怎么做、机器怎么验收、人怎么看图验收、满足什么条件放行。路线要改，先改 roadmap 再改代码；冻结后的门槛或口径变更走 [决策记录](../decisions/README.md)。

## 2. 每步执行时序与 AI 开工协议（2026-09-20 会议纪律）

每一小步的执行按以下时序，**顺序不可颠倒**：

1. **AI 开工前置阅读**：AI 必须先读完 [AGENTS.md](../../AGENTS.md)、完整路线图与本要求，然后声明"当前执行的是路线图哪一步、写入范围、依赖与前序产出版本"，再开始工作。未声明步骤的产出按越权处理。
2. **形成三个文档再动手**：该步的 ① 方案（路线图条目的具体操作）、② 机器验收规则、③ 人工可视化验收规则——三部分齐备、经确认并**落地 git 之后**，才开始执行该步。三个文档可以就是路线图条目的三个字段（见第 4 节），大步骤可拆为独立文档（如 `docs/interfaces/<阶段>.md` 执行基线），但缺一不可。
3. **双手离开键盘**：发起者不逐步指挥 AI。指令统一为"阅读项目纪律与路线图，形成当前步骤的完整方案，并遵守项目的所有纪律和路线图"；细节决策由 AI 在三文档中给出、由人评审，不在对话里碎片化下达。
4. **AI 产出必须人工核查**：AI 完成的任何产出（文档、接口、特征、模型）未经负责人人工核查前一律标"待复核"，不得标记完成或进入下一步消费；核查人记录在任务的 reviewer 字段。
5. **git 本地与远端同步**：本地每完成一个操作（三文档落地、一步执行、验收回填）即提交并推送到远端；远端是唯一共享事实，本地滞留的完成不算完成。
6. **草稿不入库**：未确认的草稿发群里或给协调者（叶安），不推 git；git 里只进"经确认的路线图、规则与验收回填"。

## 3. 两级 roadmap

| 层级 | 内容 | 维护人 | 变更方式 |
| --- | --- | --- | --- |
| 总体 roadmap | 阶段划分（R0–R6）、汇合点、阶段放行门槛、红线、分工 | 文件负责人（当前：叶安） | 团队评审 + ADR 冻结 |
| 工作线 roadmap | 本线每一步的细化条目（按第 4 节字段） | 各线负责人 | 线内可迭代；触碰公共契约或阶段门槛时升级 ADR |

总体 roadmap 不复制线内细节；线 roadmap 不得与总体阶段门槛矛盾。没有独立路线的任务（如"定评估指标"）也必须作为总路线图的一个条目出现。两者都存 `docs/plans/`，状态标注草案/已冻结。

## 4. 每个步骤条目的必备字段

| 字段 | 要求 |
| --- | --- |
| 编号/名称 | 线内唯一，如 `DATACON-001-S3` |
| 目的 | 一句话：为什么做这步、不做会怎样 |
| 负责人与依赖 | owner；依赖的前序条目与输入表版本 |
| 具体操作 | 输入（哪张表、哪个 `source_version`/`feature_version`）→ 动作（命令/脚本/流程，分步、可中断）→ 产出（文件、表、版本号）。过程性成果逐步落盘，禁止一口气黑箱跑完 |
| 机器验收 | 可执行检查：命令 + 硬断言 + 数值门槛；失败必须非零退出；新增检查须用一个构造的坏输入自证能拒绝。数值结论同时报告实测值与门槛的裕量、已知抖动；裕量 < 3×抖动记"骑线待复验"，不算普通通过 |
| 人工可视化验收 | 图集清单 + 指标表，引用 [ACCEPTANCE.md](../ACCEPTANCE.md) 第 2 节对应阶段行；图由验收脚本从同一运行导出（同源、同种子、同版本），标注样本量、单位、时间窗与一句结论。**阶段前置样张**：每阶段开工前先交付"会看哪些图 + 每张的建议通过标准"，经确认后才是该阶段的验收依据 |
| 放行条件 | 谁复核、任务状态 `review→accepted` 的条件、下一阶段准入判据 |

### 4.1 机器验收最小断言库

写任何一步的"机器验收"文档时，以下断言逐条对照，适用的必须写入（写成可执行命令 ＋ 硬断言，不用文字描述代替）：

| # | 断言 | 防的事 |
| --- | --- | --- |
| N1 | 计数一致：任何汇总／聚合计数 ＝ 逐文件、逐表计数之和 | 分块／多进程任务的计数器重复累加（2026-09-20 交付曾出现聚合计数为真实值整数倍的计数 bug，交付对数时才被发现） |
| N2 | 守恒对账：输入 − 隔离 − 去重 ＝ 输出，逐项可对账；车辆数与正类数跨版本不变 | 静默丢行、口径漂移 |
| N3 | 唯一性：主键／样本键唯一 | 重复行、错误连接 |
| N4 | 指纹：产物逐文件 md5 记录在案，抽验重算一致 | 传输损坏、文件张冠李戴 |
| N5 | 负向自证：检查对至少一个人为构造的坏输入必须失败（非零退出） | 验收器只凭自己的 PASS 自证 |
| N6 | 时点：特征计算不触 [as_of, as_of+H)；y/fold 及版本字段不入特征 | 泄漏 |

## 5. 状态回填与措辞纪律

- 每个条目带 checkbox；失败也留痕：失败→修复→复验三段都记录，不得只留最终通过。
- 未运行写 `not_run`，不写"应该没问题"；分工未定写"待定"，不虚构。
- 验收结论按 [ACCEPTANCE.md](../ACCEPTANCE.md) 四维分别报告，禁止一枚总 PASS 覆盖。
- 低级别证据不得写成高级别结论：合成数据通过 ≠ 真实数据通过；实现者自测 ≠ 独立复核；图表漂亮不构成证据。

## 7. 与既有文档的关系

- [ACCEPTANCE.md](../ACCEPTANCE.md)：定义验收证据的格式与各阶段图表要求；本要求定义 roadmap 条目必须内置验收，不重复其图表清单。
- [DATA_POLICY.md](../DATA_POLICY.md)：roadmap 及回填数值中的真实统计不入公开仓库；公开版去数值或转私有文件管理。
- [decisions/](../decisions/README.md)：口径、门槛、公共契约变更走 ADR，并列出受失效影响的实验清单。
- 治理检查与单元测试照常适用于 roadmap 文档变更。

```markdown
- 可视化验收：__ 图 × N + 指标表；阶段前置样张已确认：否
- 放行：__ 复核 accepted 后进入 __（人工核查人：__）
```
